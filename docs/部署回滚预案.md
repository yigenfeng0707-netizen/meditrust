# 医数可信 · 部署回滚预案

> 适用：docker-compose 部署形态（`--profile prod`）。目的：版本回退、
> 数据库迁移降级、备份恢复三条通路都有脚本/文档可依，出事不靠记忆。

---

## 0. 回滚决策树

```
线上故障
  ├─ 应用代码缺陷（500/功能不可用）
  │    → 通路一：应用镜像回退（分钟级，不碰数据库）
  │
  ├─ 迁移导致的数据问题（升级后报错/缺列）
  │    → 通路二：alembic 降级（先备份，再降级）
  │
  └─ 数据本身损坏/误删
       → 通路三：备份恢复（SQLite 用 backup_db.py 快照，PG 用 backup_pg.sh）
```

**总原则**：任何数据库操作之前先备份；先停写入再恢复。

---

## 通路一：应用镜像回退

每个版本构建为独立 tag（不要只用 `latest`），回退即重新指向旧 tag：

```bash
cd /srv/meditrust

# 1. 确认要回退的镜像 tag（按时间倒序列出现有镜像）
docker images | grep meditrust

# 2. 修改 .env 指定旧版本 tag（或 compose 文件 image: 字段）
#    BACKEND_IMAGE=registry/meditrust-backend:20261118-abc123

# 3. 重新部署（数据库不动）
docker compose --profile prod up -d --build backend-prod frontend-prod

# 4. 验证
curl -f http://localhost:8000/api/health
curl -f http://localhost:8000/api/health/detailed  # 确认 database available
curl -fI http://localhost:3000/
```

近似实时回退（不重建）：`docker compose --profile prod stop backend-prod` →
用旧镜像起新容器。数据库 schema 若已被新版本迁移变更，需配合通路二降级。

---

## 通路二：数据库迁移降级

`init_db` 启动时执行 `alembic upgrade head`；`scripts/alembic_rollback.py`
提供安全的反向操作。

```bash
cd /srv/meditrust/backend

# 1. 查看当前版本与历史 revision
python scripts/alembic_rollback.py --status

# 2. 降级到上一版本（脚本自动先做 SQLite 快照；PG 环境提示先跑 backup_pg.sh；
#    交互式确认 → 执行降级）
python scripts/alembic_rollback.py --down one

# 3. 或降级到指定 revision
python scripts/alembic_rollback.py --to e74955a4c306
```

⚠️ **不可逆性**：`ADD COLUMN` 的反向操作是 `DROP COLUMN`——该列数据丢失。
降级前快照保存在 `backups/pre_rollback_*.db`（SQLite）。

完整顺序：停后端 → 备份 → 降级 → 起旧镜像 → 验证。

## 通路三：备份恢复

### SQLite（小规模/演示部署）

```bash
cd /srv/meditrust/backend

# 找到要恢复的备份（每日 crontab 产生，见 backup_db.py 头部调度示例）
ls -lt backups/

# 1. 停后端
# 2. 用备份替换源库
cp backups/yibao_YYYYMMDD_HHMMSS.db yibao.db

# 3. 起后端，验证
python -c "import sqlite3; print(sqlite3.connect('yibao.db').execute('PRAGMA integrity_check').fetchone())"
```

### PostgreSQL（prod profile）

```bash
cd /srv/meditrust

# 备份（crontab 每日执行；手动补一次）
bash backend/scripts/backup_pg.sh --keep 30

# 恢复：
# 1. 停写入
docker compose --profile prod stop backend-prod

# 2. 恢复（ gzip 直接管到 psql）
gunzip -c backend/backups/pg_YYYYMMDD_HHMMSS.sql.gz \
  | docker compose exec -T postgres psql -U "$POSTGRES_USER" "$POSTGRES_DB"

# 3. 起后端，验证
docker compose --profile prod up -d backend-prod
curl -f http://localhost:8000/api/health/detailed
```

## 备份调度清单

| 库 | 脚本 | 频度 | 保留 | 执行方式 |
|---|---|---|---|---|
| SQLite | `scripts/backup_db.py --keep 30 --verify` | 每日 02:00 | 30 天 | crontab |
| PostgreSQL | `scripts/backup_pg.sh --keep 30` | 每日 02:03 | 30 天 | crontab |
| （异地） | rsync/OSS 同步 `backups/` | 每日 | 同上 | 独立任务（等保三级异地备份要求） |

恢复演练：**每季度一次**，按通路三完整走一遍并留存记录（等保三级验收要求）。

## 验证检查单（任何回滚后必跑）

- [ ] `GET /api/health` → 200
- [ ] `GET /api/health/detailed` → database available
- [ ] `GET /metrics` → 应用存活（Prometheus 告警自停）
- [ ] 抽查业务接口（如 `GET /api/users/user_001/profile`）数据完整
- [ ] 查最近日志：`docker compose logs --tail 100 backend-prod`
      （JSON 格式，可按 `request_id` 字段检索定位）
